## 1. 動機與範圍

原設計的核心敘事是「你剛駭進一台機器，正在讀上面的檔案」（見前置文件 2.6）。但首頁實際呈現的是一段 `$ cat ~/.profile` 的靜態輸出——**檔案的比喻只停在文字層，沒有做實**。

這次把它做實：首頁的抖色背景成為桌布，桌面上放一個叫 `.profile` 的檔案圖示，點開跳出 TUI 編輯器視窗。

### 範圍

**做**：桌面圖示、vim 風格編輯器視窗、開關互動、窄畫面的展開版面。

**不做**（明確排除）：
- 檔案總管／多檔案清單——桌面上只有 `.profile` 一個圖示
- 視窗管理器——不可拖曳、不可縮放、不可疊，同時只有一個視窗
- 可編輯內容——唯讀（見 §5）
- 檔案 metadata（行數、位元組數）——見 §2 的決策紀錄

### 不變的部分

背景完全不動：抖色渲染、入侵序列、KEHAO 字標、五段時序、WebGL 取景，一律沿用。這次只換掉前景中那個固定在左下角的終端機視窗。

## 2. 決策紀錄：不做檔案 metadata

設計過程中曾提案把 profile 內容搬進 `src/data/profile.{en,zh}.txt`，建置時讀入並計算行數與 UTF-8 位元組，讓狀態列顯示 vim 開檔時的 `"~/.profile" 5L, 218B`。

**否決。** 那個數字把重點從「點開一個檔案」轉移到「展示檔案 metadata」，讀起來像 `ls -l` 的輸出而不是一個可以打開的東西。它是為了視覺擬真而生的細節，不是這個想法本身。

連帶結論：
- 內容留在 `index.astro` / `zh/index.astro` 現在的位置，不搬進資料檔
- 不需要 `parseProfile()` 之類的建置期模組，也不需要對應的單元測試
- 行號用 CSS `counter-increment` 生成——CSS 生成內容本來就不進無障礙樹，連 `aria-hidden` 都省了

同一個判準適用於狀態列右下角的 `1,1 All`：它只有在 vim 鍵位生效時才會動，而鍵位是選配、手機上完全不存在。**在多數情境下永遠不動的數字就是死掉的裝飾**，不放。狀態列只放檔名。

## 3. 版面

### 3.1 桌面（> 640px）

```
┌──────────────────────────────────────┐
│ ▤                                    │
│ .profile                             │
│                                      │
│            K E H A O                 │
│         // HAPPY HACKING             │
│                                      │
│   ┌─ ~/.profile ──────────────[x]┐   │
│   │  1 Cloud-native & AI infra...│   │
│   │  2 I build the boring parts  │   │
│   │  3 that let the interesting  │   │
│   │  4 parts stay up.            │   │
│   │  5                           │   │
│   │  6 STATUS ONLINE · TAIPEI    │   │
│   │  ~                           │   │
│   │  ~                           │   │
│   └─ ~/.profile ─────────────────┘   │
└──────────────────────────────────────┘
```

圖示固定在桌面左上（導覽列下方）。視窗關閉後圖示仍在，隨時可再點開。

### 3.2 窄畫面（≤ 640px）

沒有圖示、沒有 `[x]`、視窗恆開。就是現有堆疊版面裡的那個區塊換上編輯器 chrome，原生觸控捲動。

理由：桌面隱喻需要「圖示與視窗是兩個東西」這個空間關係，320px 放不下；而把自我介紹藏在一次點擊後面，在手機上是實質的內容損失。這與前置文件 §6 的漸進退化原則一致——**能力不足時退回更簡單但完整的形態，不退回殘缺的形態**。

## 4. 元件邊界

| 元件 | 職責 | 依賴 |
|---|---|---|
| `DesktopIcon.astro` | 桌面圖示。`<button aria-expanded aria-controls>`，≤640px `display: none` | 無 |
| `VimWindow.astro` | 編輯器 chrome：標題列（含 `[x]`）、行號欄、`~` 填充行、底部檔名列。純呈現，內容走 slot | 無 |
| `src/lib/profile-window.ts` | 開關互動：圖示點擊、`[x]` 點擊、鍵盤。切換 wrapper class 並同步 `aria-expanded` | 無 |

`VimWindow` 不知道 `.profile` 的存在，也不知道桌面圖示的存在——它收一個 `path` 與一段內容，畫出一個編輯器。兩個 `.astro` 元件都不持有狀態：開關是 wrapper 上的一個 class，由 `profile-window.ts` 單獨負責切換。

`[x]` 由 `VimWindow` 畫，但在 ≤640px 以 CSS 隱藏——窄畫面沒有「關閉」這個狀態（§3.2）。

`profile-window.ts` 與 `site-dither.ts`、`nav-glitch.ts` 同層：有 DOM 副作用、沒有純函式可抽，因此不寫單元測試，行為由 e2e 涵蓋。

`~` 填充行由 CSS 生成，不寫進 HTML：它是「檔案結束後的空白」這個 vim 慣例的視覺表現，不是內容。

### 配色

行號欄與 `~` 填充行用 `--muted`，**不用 `--dim`**。`--dim` 在 `--panel` 上只有 4.91:1，是今天才修正到 AA 的邊緣值（見 `tokens.test.ts`），新增的小字不該再貼著門檻走。

## 5. 狀態與漸進增強

倒過來做：**HTML 預設就是視窗開著**，JS 只負責把它收起來再彈開。

| 情境 | 行為 |
|---|---|
| 無 JS | 圖示在、視窗開著、內容看得到。零退化 |
| 有 JS，序列會播 | 既有的 `html.seq-pending` 順便把視窗收起，SETTLE 移除 `seq-pending` 時彈出 |
| 有 JS，序列不播（同 session 第二次進首頁） | 沒有 `seq-pending`，視窗直接是開的 |
| 點 `[x]` 或圖示 | 切換 wrapper 上的 class |

**不新增第二套時序**——彈出時機掛在既有的 `seq-pending` 機制上，不另外排 timer。這避免了與入侵序列打架，也避免了再一個需要被取消的 `setTimeout`。

**不存 sessionStorage**：換頁回首頁時重置為開啟。視窗活在 `main.page` 裡（換頁會被 swap），不在 `#fx`（`transition:persist`）裡，所以天生不會有跨頁殘留狀態——這正是先前 C1 缺陷的成因，不重蹈。

## 6. 鍵盤（選配，僅桌面）

**觸控與滑鼠是第一等公民。這一整節掛掉不影響任何人能不能用。**

| 鍵 | 行為 |
|---|---|
| `j` / `k` / `↑` / `↓` | 捲動 |
| `gg` / `G` | 跳首 / 跳尾 |
| `:q` / `ESC` | 關閉視窗 |

必須在入侵序列的「按任意鍵跳過」之後才綁定，否則兩者互搶按鍵。窄畫面不綁——那裡沒有視窗可關，也沒有實體鍵盤。

## 7. 測試

**單元**：無。這次沒有純函式模組（見 §2）。

**e2e**：
- 無 JS 時視窗是開的，且 profile 內容在畫面上
- 點 `[x]` 關閉、點圖示開啟，`aria-expanded` 跟著變
- ≤640px 圖示不可見（`display: none`，仍在 DOM 中——斷言用不可見而非不存在），且視窗恆開：沒有任何可見控制項能把它關掉
- 序列播放期間視窗不顯示，SETTLE 後出現
- `ESC` 關閉視窗（桌面）
- 既有的窄畫面護欄（`mobile-layout.spec.ts`）仍須全綠——特別是「字標與視窗不重疊」

**Lighthouse**：既有的 `color-contrast: minScore 1` 硬門檻自動涵蓋新增的 chrome，不需新增設定。
